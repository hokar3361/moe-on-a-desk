# moe-on-a-desk-4-wsl 設計と実測ログ

計測方法は moe-on-a-desk と同じ(bench-strata 1K/4K `--max-tokens 256 --repeat 3`、コード・文章 400 トークン greedy、サーバの timings、思考なし)。
スクリプトは WSL の `~/abw.sh`(資源も 1 秒ごとに記録:CPU 使用率は 32 スレッド全体を 100%、RSS はサーバのプロセス、VRAM は使用量)。
ビルド:`~/m125w/base`(未改造 781dbc5、CUDA sm_89)、`~/m125w/ours`(781dbc5+moe-on-a-desk のパッチ 55 本+CUDA 向け修正)。

## §1 モデルの形(Flash GSQ-RCO IQ3_XXS)

- 48 層、エキスパート 512 個中 10 個、隠れ 2560、エキスパートの中間 640。
- 1 層あたりのエキスパート:gate/up は IQ2_XS(各 242 MB)、down は IQ4_NL(472 MB)→ **1 エキスパート 1.87 MB、1 層 957 MB、全 45.9 GB(42.9 GiB)**。
- 1 トークン(B=1)で 480 エキスパート= 約 0.9 GB を読む。全部 PCIe(実効 約 20 GB/s)で運ぶと 約 45 ms/トークン [計算]。

## §3 私たちのパッチの CUDA での不具合(修正済み)

- 症状:私たちの版は CUDA で、短いプロンプトから約 256 トークン目に `illegal memory access`/`unspecified launch failure` で落ちる(キャッシュの有無に関係なし)。
- 原因:QSA の「全プールが選ばれるときは選択マスクの代わりに因果マスクを使う」省略(`LLAMA_QSA_DENSE_SHORT`、Metal でビット一致を確認済み)。
  CUDA の疎な flash attention 経路と組み合わせると落ちる。`LLAMA_QSA_DENSE_SHORT=0` で解消。
- 修正:Apple 以外では既定で無効(`#ifdef __APPLE__`)。Mac の動作は変わらない。WSL のコミット 4ef484011。

## §5 1 ラウンドの内訳(コード、MTP 3、キャッシュ 14 GB)

計測用の仕組み(すべて既定で無効):`LLAMA_MOE_CACHE_LOG=N`(当たり率・転送量・コールバック内の時間)、`LLAMA_UBATCH_TIME=N`(幅ごとの 1 回の時間)、
`GGML_SCHED_PROF=N`(+`GGML_SCHED_PROF_SYNC=1` で分割ごとの GPU 時間)、`GGML_CUDA_OPPROF=N`(演算ごとの GPU 時間、CUDA グラフを外すので絶対値は参考)。
WSL の Nsight Systems は CUDA API しか記録できず、カーネルの記録は取れない。

- 本体の検証(B=4)53 ms+下書き 約 1 ms×3〜4 → 1 ラウンド 約 57 ms、受理 3.7 → 65 tok/s [実測]。
- 当たり率 83〜91%、1 層あたり 3.4〜7.9 MiB(1.8〜4 エキスパート)を転送。転送は**ページ固定なしの mmap から 12.7 GB/s、CPU が完了まで待つ**(1 層 0.27〜0.69 ms)。
- CPU 側(nsys の CUDA API):転送 43%、GPU 待ち 34%、CUDA グラフの起動 11%(1 回 51 µs、WSL では重い)、隙間 10%。
- 分割は 1 グラフあたり 49(48 層の MoE ごと+CPU 1)。上流のスケジューラは分割の境目ごとに GPU を待ち切る(イベントなし)。

## §6 ページ固定(採用)

- 小テスト(`~/wslb/bw.cu`、1.87 MB をランダム位置から):普通の mmap 14.1 GB/s、`cudaHostRegister` した mmap **22.7 GB/s**(8 GB の登録 0.1 s)、
  cudaMallocHost 22.9 GB/s、CPU で中継バッファへ写してから送る方式は 8〜12.5 GB/s。
- 上流には `ggml_backend_cuda_register_host_buffer`(`GGML_CUDA_REGISTER_HOST` で有効)があるが、どこからも呼ばれていない。
- 新しい仕組み `LLAMA_MOE_CACHE_PIN=1`:キャッシュの初期化時に、キャッシュ対象の層のエキスパートの mmap 範囲(144 範囲、39.97 GiB)をページ固定。0.7 s。
  転送が DMA で非同期になり、CPU は待たない。
- 効果 [実測]:検証(B=4)53 → 39 ms、コード 65〜69 → 83 tok/s(計測用ログあり)。
- 費用:モデルファイルのページキャッシュ 40 GiB が固定され、解放できなくなる(RSS は元から 46 GB)。

## §7 次の層の先読み(否定)

- 仕組み `LLAMA_MOE_CACHE_PREFETCH=K`:層 il の MoE 入力に層 il+1 のルーターを当てて上位 K を予測し、足りない分を同じ GPU の別ストリームで先に送る
  (主ストリームは次の転送の前にイベントを待つ)。GLM(Mac)では効いた方式。
- 予測の当たり [実測]:実際に選ばれた (トークン, エキスパート) のうち、予測上位 10 に入るのは 55.5%、上位 32 で 81.3%。
  Flash はハイパーコネクションで層ごとに隠れ状態が大きく変わり、隣の層の予測が弱い。
- さらに、本当に足りないのはまれなエキスパートで、予測で拾えるものはほぼ既にキャッシュにある(上位 10 で 1 層あたり 0.15 MiB しか送らない)。
- 結果:当たり率は変わらず、検証は 38 → 42〜47 ms と遅くなった(予測の演算と別ストリームの費用)。Flash では打ち切り。

## §8 GPU 計算の下限

- `GGML_SCHED_PROF_SYNC`:MoE を含む分割(1 層ぶん)の GPU 時間は 0.72 ms、うち転送 約 0.22 ms → **計算 約 0.5 ms/層、検証 1 回 約 24 ms**。
- 1 分割あたりのカーネル数 約 71 → 1 カーネル平均 約 7 µs。重みの読み出し量(非エキスパート 約 4 GB/トークン幅に依らず+選ばれたエキスパート)から見た下限は 4〜5 ms [計算]。
- 全部当たった場合(bench の 2 回目以降に近い)の検証 約 27 ms が、今のカーネル構成での天井。→ 次の大きな手は CUDA 側のカーネル融合(Mac で Metal に行ったことの移植)。
- 補正(後の計測):CUDA グラフ内の極小カーネルは 1 個 約 1.1 µs(`~/wslb/graphk.cu`)。グラフ内に時刻記録ノードを入れると 1 個 約 11 µs 上乗せされるので、
  カーネルごとの GPU 時間(`GGML_CUDA_GPROF`)は当てにならない。記録の数を変えた 2 回から外挿すると **1 層の GPU 計算は 約 0.29 ms**。
  分割 1 回の所要 0.72 ms = 転送 約 0.22+計算 約 0.29+**層ごとの CPU との往復(同期・ID の読み出し・グラフの起動 51 µs)約 0.2 ms**。
- bf16 の小さな行列積(2560×1、10240×4 など)は単独で測ると 3〜5 µs(`~/wslb/mmbench.cpp`)。モデル内の振り分け(mmvf / mmf)も同じで、異常ではなかった。

## §9 GPU 側の引き当て `GGML_OP_MOE_FETCH`(採用、`LLAMA_MOE_CACHE_FETCH=1`)

観測:層ごとに「GPU を止めて CPU が選ばれたエキスパートを読み、足りない分を送ってからグラフを起動する」往復が 1 層 約 0.2 ms、48 層で 約 10 ms。
→ 足りないエキスパートの判断と取り寄せを GPU 自身に行わせ、1 回の検証を分割なしの 1 つのグラフで流す。

- 新しい演算(フォーク、CUDA のみ):層の選択 ID → キャッシュの枠。1 ブロックの計画カーネルが、ID ごとに枠表を引き、無ければ
  グループ共通の空き枠プールから枠を取って枠表を書き換え(足りなければ一時枠)、記録(トレース)と取りこぼし一覧を書く。
  続くコピーカーネル(12 ブロック固定)が、取りこぼしのエキスパートを**ページ固定した CPU メモリから GPU が直接読んで**枠へ書く。
- CPU 側(検証の合間、`begin_forward`):トレースを読んで LRU を更新(当たり=touch、新規=枠の割り当てを確定)、空き枠プールを LRU の古い順に補充、
  枠表(ホストが正)と空き枠を GPU へ書き戻す(状態 約 170 KB の読み書き)。大きなバッチ(プロンプト読み込み)は従来の経路のまま。
- WSL では登録したホストのアドレスをカーネルがそのまま使えない(`canUseHostPointerForRegisteredMem` = 0)→ `cudaHostGetDevicePointer` の値を
  CUDA バックエンドの新しい関数 `ggml_backend_host_buffer_device_ptr` で取り、エキスパートごとの所在表(desc)に入れる。
- GPU から CPU メモリを直接読む速さ(`~/wslb/zcopy2.cu`):全体 10〜20 ブロック(256 スレッド)で 21〜22 GB/s(DMA と同等)、多すぎると 11〜15 GB/s。
- つまずき:(1) 層ごとの空き枠 8+一時枠 64 → 当たり率が下がった。(2) このモデルはエキスパートの型の組が層ごとに違い**キャッシュが 10 グループ**に分かれる。
  グループごとに 256+64 枠を空けていたため容量の約 4 割が空だった → 空き枠は直近の取りこぼしのピーク×1.5(最小 8)に自動調整、一時枠 24。
- 出力:ページ固定+DMA の版と **md5 一致**(同じエキスパートを同じ計算で使う)。
- 検証(B=4)39.5 → 35.5 ms。残りの内訳 [計算]:取りこぼしの読み込み 約 19 ms(1 層 4〜5 個、1 回 約 400 MB を 21 GB/s)+計算 約 14 ms。

|---|---:|---:|---:|---:|---:|---:|---:|
| 比較元:未改造+キャッシュ+MTP 3(MTP 2/4/5 はこれより遅い) | 116.7 | 115.3 | 64.6 | 63.1 | 3% | 46 GB | 23 GB |

## §10 入れ替え方針・容量・MTP の大きさ

- ルーティングの記録(`LLAMA_MOE_TRACE`、上の 12 プロンプト、51,168 層×回)で方針をシミュレーション(`~/wslb/cachesim.py`):
  LRU 3.08 取りこぼし/層、減衰つき LFU 3.09〜8.81、**Belady(未来を知る最適)1.58**。現実的な方針で LRU を大きく超えるのは難しい。
- 容量の効き方(LRU):×0.9 で 3.58、×1.1 で 2.68、×1.25 で 2.21、×1.5 で 1.67 → 容量 10% で取りこぼし 13〜15%。
- VRAM の内訳:本体の非エキスパート 3.66 GB、キャッシュ+KV 14.9 GB、計算 0.58 GB、**MTP 3.29 GB(エキスパート 512 個 Q8 が 2.55 GB)**。
- MTP のエキスパートだけ Q4_K(down は列数 640 の都合で Q5_0)に再量子化(`mtp-…-Q8e4.gguf`、4.14 → 2.98 GB)。下書き専用なので本体の出力は不変
  (MTP 4 同士で md5 一致)。受理長も同じ(4.53 / 2.66)。固定指標 130.8 / 139.5 / 95.3 / 81.1、**VRAM 23 → 22 GB**(余力の基準を満たす)。
- 浮いた分をキャッシュへ(14,000 → 15,100 MiB)は逆に遅い(120.3 / 130.9 / 85.6 / 67.0、VRAM 23 GB)。満杯近くで Windows 側の退避が起きると推定。

## §11 計算の内訳(ルーティング固定・全部当たり、計測専用 `GGML_MOE_FETCH_FIXED=1`+`GGML_CUDA_SKIP=…` で飛ばした分の差)

全部当たりの 1 回:1 トークン 13.6 ms、4 トークン 17.2 ms(MTP なし、プロンプトキャッシュなしで同じ短いプロンプトを繰り返す方法)。
