# Mac Studio 64GB で 125B を超高速に — 設計書

普通の 64GB Mac で 125B クラスの MoE を実用以上の速度で動かす。
Strata が「普通のゲーミング PC」で実現したことの Mac 版を作る。

本書は理論(計算)・仮説・実測を区別して書く。
**[実測]** は Mac Studio 上で測った値、**[計算]** は実ファイルとハード仕様からの算出、
**[仮説]** は未検証の見込み。

## 1. 前提(固定)

| 項目 | 内容 |
|---|---|
| 機材 | Mac Studio M4 Max 64GB(帯域 546 GB/s、GPU 上限 55.66 GB [実測]) |
| モデル | Qwen3.8-Flash-Next 125B(6B active、512 エキスパート中 10 使用、48 層) |
| 量子化 | IQ3_XXS(ISTA-DASLab GSQ-RCO)。本体 43.8 GiB は GPU、n-gram 26.8 GiB は CPU/SSD |
| 指標 | 単一ストリームの decode tok/s(1件の回答の速度) |
| 品質 | 基準線と greedy 出力が一致すること。量子化はこれ以上下げない |
| 基準線 | 素の llama.cpp 781dbc5(Metal)、投機なし |
| 実験規則 | 機材・モデル・量子化・プロンプトを固定し、変えるのは1要素だけ。毎回出力一致を確認 |

IQ3_XXS の品質(Q4_K_XL 比、コード 2 万トークン)[実測]:
top-1 一致率 95.1%、パープレキシティ +2.7%、KL 平均 0.102(中央値 0.0003)。

### 2.2 新しい仕組み:常駐メガカーネル [計画]

層の処理全体を 1 回のディスパッチにし、段の同期を GPU 内のアトミック同期で行い、次の段の重みを同期の前から
読み始める(重みは活性値に依存しないため)。部品は実測で確認済み(§4.4):同期 0.78 µs、
`coherent(device)` + デバイスフェンスで段をまたぐ受け渡しの不一致 0、常駐内の 6.4 MB 段 13.8 µs(476 GB/s)。

見積もり(修正、2026-10-10):境界 1 つの最低コストは約 2 µs(spin 待ち下、シリアル型エンコーダでも 1.9 µs)、
常駐内の同期は約 1 µs。同期の置き換えだけなら削減は境界あたり 1〜1.5 µs にとどまる。主な効果は、
**早く終わったスレッドグループが同期待ちの間に次の段の重みを先読みし、立ち上がり損失を消すこと**に期待する。

4 トークン検証パス 34.1 ms の内訳 [実測]:境界 10.6 ms、Dense 14.5 ms(265 GB/s)、MoE 12.5 ms、その他 2.9 ms。
3 倍には検証パス 約 16 ms が要り、3 つすべてを半分以下にする必要がある:
境界 → メガカーネル+先読み、Dense → 複数トークン 1 回読み+先読みで約 450 GB/s、
MoE → 型別カーネル(展開表をスレッドグループメモリ)を複数トークン対応に。下書きグラフ(2 ms × 約 4 回/サイクル)も対象。

否定済み(このセクションの作業中):汎用展開関数による複数トークン MoE カーネル(34.0 → 44.7 ms、
`constant` 表のばらばらな参照が遅い)、シリアル型エンコーダ(境界 −0.4 µs のみ、並行性を失う)。

### 2.4 段列の再生による上限の確定 [実測、2026-10-10] — メガカーネルは主因ではない

実グラフの段列(1795 段、段ごとの重みバイト数)を、理想的な読み出しカーネルで再生した(/tmp/replay.m)。

| | B=1 相当(4.25 GB) | B=4 相当(6.21 GB) |
|---|---:|---:|
| 現行方式(起動+バリア) | 11.63 ms | 15.49 ms |
| 常駐メガカーネル | 10.48 ms | 14.29 ms |
| 帯域の下限 | 7.79 ms | 11.37 ms |
| **実際のエンジン** | **20.9 ms** | **34.1 ms** |

- **メガカーネル化の効果は 1.1〜1.2 ms にとどまる。** 先読みは逆効果。§2.2 の計画は撤回する
- **無駄の本体はカーネル自体の非効率**(B=4 で 34.1 − 15.5 = 約 18.6 ms)
- 全カーネルが理想値になれば検証パス 約 15.5 ms → MTP 込み 約 155〜160 tok/s(下書き側も同様に改善した場合)

B=4 で見つかった非効率な起動形状 [実測]:`hc_inject`(bf16)と `shared_expert_gate` が 1024 スレッドの
グループ 1 個だけ(1 パス 95 回 + 47 回)。HC の down 行列(6.5 MB)が 40 グループのみ。MoE の down(iq4_nl)は
4 行だけを処理する極小グループが 1 回 24,533 個。

切り分け実験:MoE down の 1 simdgroup あたりの行数を 2 → 8 にすると 2.38 → 1.41 ms(−41%)。
→ MoE は展開演算ではなく、**極小グループのセットアップ・起動コスト**に律速されている(定数変更は戻した。
成果ではなく、新しいカーネル設計の根拠)。

### 2.5 次の作業:少数トークン(1〜8)専用カーネル群

目標値は再生の理想値。カテゴリ別の B=4 実測 → 理想:MoE 12.5 → 約 5 ms、Dense 14.5 → 約 8.5 ms
(bf16 4.6 / q6_K 3.0 / q5_K 1.6 / iq4_xs 1.6 / q4_K 1.5)、境界・小演算 約 7 → 約 4 ms。
設計原則(実測から):1 グループの仕事量を十分大きくして起動・セットアップを償却する、全コアを埋める
グループ数を確保する、重みは 1 回だけ読み全トークン分を積和する。
進め方:FFN 半分(HC 混合 → ルータ → top-k → 共有エキスパート → ルーテッドエキスパート → 合算 → HC_POST、
現状 17 段)を 1 ディスパッチにするところから始め、層出力を既存経路と突き合わせて正しさを確認しつつ広げる。
段階 2 の基準は「同一機・同一条件で実測した MLX 系の最高値を超える」に置き直す
(公開値は測定条件がそろっていないため、この Mac で実測して基準線にする)。

## 3. 理論:1トークンで何を読むか [計算]

GGUF の実テンソルから算出。

| 部位 | 量子化 | 1トークンあたり |
|---|---|---:|
| hyper-connection 重み(hc_attn/ffn × up/down、48 層) | **BF16** | 1.17 GiB(27%) |
| ルータ(ffn_gate_inp) | **BF16** | 0.12 GiB(3%) |
| 注意・GDN・共有エキスパート等 | Q4〜Q6、IQ3/IQ4 | 1.88 GiB(43%) |
| 出力ヘッド | Q5_K | 0.41 GiB(9%) |
| ルーテッドエキスパート(10/512) | IQ3_XXS | 0.78 GiB(18%) |
| **合計** | | **4.36 GiB = 4.68 GB** |

- **帯域の壁:** 4.68 GB ÷ 546 GB/s = **8.6 ms/パス → 117 tok/s**(投機なし)
- **注目点:** 読み出しの **約3割が未量子化の BF16**。他はすべて 3〜6bit

## 4. 現状の時間の使い方 [実測 + 計算]

| | 1パスの時間 | 壁(8.6 ms)との差 |
|---|---:|---:|
| 素の llama.cpp(39.6 tok/s) | 25.3 ms | **16.7 ms が帯域以外に消えている(利用率 34%)** |
| + MTP(57.8 tok/s、2.93 トークン/パス、採択率 65%) | 50.7 ms | 素の 1 パスの 2.0 倍 |

MTP の出力は基準線と完全一致 [実測]。

16.7 ms の内訳の仮説 [仮説]:

- **H1 カーネル起動の多さ:** 1 層あたり数十個、48 層で 1 トークンに千数百のカーネル。batch 1 では起動・同期のコストが帯域を遊ばせる
- **H2 細長い BF16 行列の効率:** hyper-connection は 10240×320 と 320×10240。1 行が短く、Metal の行列ベクトル積カーネルが帯域を使い切れない
- **H3 IQ3_XXS 展開の演算コスト:** MoE カーネルで展開が律速になる

### 4.1 切り分けの結果 [実測、2026-10-10]

Metal のコマンドバッファの GPU 時刻(GPUStartTime/GPUEndTime)を計測する計装をエンジンに追加し、
decode 1 トークン分のグラフを測った。

- CPU 側(コマンド作成)1.9 ms、**GPU 側 23.4 ms**。律速は GPU 側
- 1 トークンあたり **カーネル 3358 個、依存段(バリア)2020 段**

除外実験(その演算を発行しない。結果は壊れるが時間だけを見る)。計測用スイッチ
`GGML_METAL_PROF_SKIP` / `GGML_METAL_PROF_NOBARRIER` をエンジンに追加した。

| 除外したもの | GPU 時間の減少 | 読み出し量と理想時間(546 GB/s) | 効率 |
|---|---:|---|---:|
| バリア全部 | −7.5 ms | — | 1 段あたり平均 3.7 µs |
| Dense の行列ベクトル積すべて(785 個) | −12.0 ms | 3.84 GB → 7.0 ms | 58% |
| うち BF16(HC・ルータ) | −5.1 ms | 1.39 GB → 2.5 ms | 50% |
| MoE エキスパート(MUL_MAT_ID) | −3.4 ms | 0.84 GB → 1.5 ms | 45% |
| HC_PRE / HC_POST / SCALE | −1.3 ms | ほぼ 0 | — |
| MUL / ADD | −1.8 ms | ほぼ 0 | — |

M4 Max でのマイクロベンチ(Metal 直書き):

| 1 段の内容 | バリアあり | バリアなし |
|---|---:|---:|
| 極小カーネル | 1.5 µs | 0.17 µs |
| 6.5 MB 読み出し(DRAM) | 18.2 µs(375 GB/s) | 12.7 µs(536 GB/s) |
| 20 MB 読み出し(DRAM) | 44.5 µs(471 GB/s) | — |
| 6.5 MB 読み出し(SLC に常駐) | 7.8 µs(880 GB/s) | — |

SLC の実効容量は 26〜53 MB の間(26 MB までは常駐、53 MB で DRAM 速度に戻る)。

仮説の判定:

- **H1(カーネル数)は棄却。** G3 融合で並行実行中の 288 カーネルを消しても GPU 時間は不変(23.58 → 23.62 ms)
- **H1'(依存段数)を支持。** コストはカーネル数ではなく、直列に並ぶ段の数に比例する。1 段ごとに GPU が空になり、DRAM の立ち上がりもやり直しになる
- **H2(細長い BF16)を支持。** 効率 50%
- **H3(MoE)** は効率 45%。展開コストか段の固定費かは未分離

1 層あたりの依存段 [実測]:GDN 層 約 34 段、QSA 層 約 60 段。内訳は HC 混合 6 段 × 2、
GDN 注意 11 段、QSA 注意 約 40 段(うちインデクサとマスク作成の小演算が約 25 段)、FFN 11 段。

### 4.2 否定された案 [実測]

- **重みの先読み(同一キュー内):** 次の行列を SLC に先読みするカーネルを並行に発行した。Metal のバリアはリソース限定(`memoryBarrierWithResources`)でも先行ディスパッチ全部の完了を待つため、先読み分が段の時間に上乗せされ悪化した(18.4 → 25 µs/段)
- **重みの先読み(別キュー):** 2 本目のコマンドキューで先読みし、GPU 上のカウンタで歩調を合わせる方式。2 本のコマンドバッファは並行実行されず直列化されたため成立しない

したがって、依存チェーンの裏で DRAM を流し続ける方式は、別ディスパッチでは使えない。
(1 つのディスパッチ内なら可能。§4.4)

### 4.3 SoC のクロック状態 [実測、発見]

同じカーネル・同じデータでも、GPU にかかる負荷の時間的な形で帯域が最大 2 倍変わる
(6.5 MB 段:間欠負荷 30.3 µs、連続 17.9 µs、十分温まった後 15.0 µs)。

推論中は CPU スレッドが GPU 完了をブロッキング待ちで寝るため、CPU が全コア休止になる。
このとき SoC はファブリック/メモリのクロックを下げ、GPU の帯域まで落ちる。

| 並行して CPU にかけた負荷 | GPU 時間/トークン |
|---|---:|
| なし | 23.44 ms |
| メモリを使わない 1 スレッドの空回し | **21.15 ms(−10%)** |
| メモリ読み出し 166 GB/s(帯域を奪う) | 21.57 ms |

→ CPU の活動状態が効いている(メモリ需要ではない)。
**対策:エンジンの GPU 完了待ちを、状態ポーリングによるスピン待ちに変更**(CUDA の
cudaDeviceScheduleSpin と同種の手法)。計算は一切変わらないため出力は完全一致。
`GGML_METAL_SPIN_WAIT=0` で従来動作。

### 4.4 常駐カーネル(1 ディスパッチ内のグリッド同期)[実測]

全スレッドグループが常駐できる規模で 1 回だけ起動し、段の同期を GPU 内のアトミックカウンタで行う。

| 1 段 | 起動+バリア | 常駐+グリッド同期 |
|---|---:|---:|
| 同期のみ | 1.5 µs | 0.78 µs |
| 6.4 MB 読み出し | 18.2 µs | 13.8 µs |

正しさ:段をまたぐデータ受け渡しは、`coherent(device)` とデバイス範囲フェンスの併用で
不一致 0(どちらか片方だけでは大半が不一致)。

HC 混合部(6 段)を常駐カーネル 1 本にした実装は、段数 −494 だが速度は元のカーネルと同等以下
(1 回 43 µs 対 40 µs)。同じ重みの単純連続読み出しは同じカーネル内で 13.8 µs なので、
差は付随処理にある。既定では無効(`GGML_METAL_HC_MIX=1` で有効)。

### 4.5 MTP の 1 サイクル [実測]

| グラフ | 1 回の GPU 時間 | 比率 |
|---|---:|---:|
| 検証パス(約 4 トークン) | 36.0 ms | 84.5% |
| 下書き(MTP ヘッド) | 2.04 ms × 約 3.9 回 | 15.5% |

単一トークンのパス 21.9 ms に対し、4 トークンは 1.65 倍。増分の内訳:MoE +8.3 ms、
Dense +2.4、バリア +1.9、SSM_CONV +1.45。

- 実際の検証パスで、4 トークンが選ぶエキスパートの異なり数は平均 69.7%(40 組中 約 28)
- 重複エキスパートを 1 回だけ読むカーネルを実装 → **速くならない**(36.2 → 37.5 ms)。
  MoE カーネルは DRAM 帯域ではなく、展開・遅延に律速されている(B=1 で実効 190〜340 GB/s)

### 4.6 グラフの依存深さ [実測]

計算ノード 4363 個のデータフロー上の最長経路は 2343 段(うち 1314 段は 1 ノードのみ)。
現行の段数(融合込み 2009)はこの下限にほぼ一致。**スケジューリングの改善では段は減らない。**
段を減らすには、依存する演算を 1 つのカーネルの中で処理する(融合・常駐カーネル)しかない。

## 5. 手法と、それぞれが動かす数字

| 手法 | 何を作るか | 動かす数字 | 見込み [仮説] |
|---|---|---|---|
| **② 帯域利用率** | qwen4exp の decode 経路を M4 Max 向けに作り直す(カーネル融合、細長い BF16 用カーネル)。H1〜H3 のうち実測で大きいものから | 1 パス 25.3 ms → 11 ms(利用率 78%) | 素で 91 tok/s |
| **MTP 下書きコスト削減** | MTP の 1 パスを素の 2.0 倍から 1.5 倍へ(下書き層の読み出し削減) | 1 パスあたりのコスト倍率 | ②と合わせて約 175 tok/s |
| **③ BF16 の可逆圧縮** | BF16 テンソル(読み出しの 3 割)を指数部のエントロピー符号で可逆圧縮し、遊んでいる演算で展開する | 読み出しバイト 4.36 → 約 3.96 GiB | 約 1.1 倍。**出力は完全に同一** |
| **① 1件の分割並列** | 1 件の回答を独立部分に分け、同時に生成する | 1 ステップあたりの有効トークン数 | 段階 3 に必要(下記) |

### 300 tok/s の条件 [計算]

MTP の検証パス(約 4 トークン)は、Dense 3.58 GiB を 1 回、エキスパートを約 3 倍、
下書き層を数回読むので、約 7.1 GiB。帯域 100% でも 13.9 ms で、
**2.93 トークン/パスなら単一ストリームの天井は約 210 tok/s**。

300 に届かせるには、次のいずれかが追加で要る。

- ③で読み出し自体を減らす
- ①で 1 ステップに載る有効トークンを増やす(4 分割なら、帯域 100% で約 317 tok/s 相当)
- 採択数の多い下書き器

  公式は M3 Ultra 上の模擬で decode 36.8〜42.5 tok/s(常駐時の 0.31〜0.39 倍)。第三者の実機(M5 Pro 64GB、Issue #95)で

- 常駐時:M3 Ultra(819 GB/s)で 108〜142 tok/s(v0.3.4.1、条件不明)。
- 判断:この Mac・64GB という制約での TensorFold の公開値(19〜45)は私たちの値(61〜116)より低い。ただし量子化(4-bit vs IQ3_XXS)と
  機材が異なり、同条件の比較ではない。都合の良い解釈を避けるため、同じ Mac で TensorFold を実測するまでは「上回った」とは書かない。
- 取り入れる候補:`--ple-on-ssd`(n-gram 表を SSD から、decode 0.91〜1.03 倍)、MTP チェーンの確信度打ち切り、プレフィックスキャッシュ
  (固定指標の繰り返しを利用することになるため、評価には使わない)。

### 9.10 iq3_s の展開とレジスタ削減(2026-10-11)[実測]

修正:融合の条件に「第 2 出力が x・residual・post・第 1 出力と重ならない」ことを追加。遅延なしで ub=512 / 64 とも 1.2282、verify.sh 一致。
以後の検証手順に「遅延なしの PPL(c=512、ub 512 と 64)が開始時点と一致」を加える(B=1 の md5 と固定指標の文面だけでは大きなバッチの不具合を検出できない)。

- QSA マスクを選択セルの生の索引から直接散布(`LLAMA_QSA_SIMPLE_MASK`、既定 on):死んだスロットは番兵行(n_kv、表示範囲外)か、因果マスクで −inf のセルを指し、
